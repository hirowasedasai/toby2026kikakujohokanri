# 運用フロー

## 初回構築

1. 管理者がstaging用とproduction用に別々のGoogle Spreadsheetを用意し、それぞれにcontainer-bound Apps Script projectを作る。
2. 各Spreadsheetに入力5タブを正しいフォーム連携で用意する。スクリプトからは作成しない。
3. 各projectのScript Propertiesへ`APP_ENV`、`EXPECTED_SPREADSHEET_ID`、`RELEASE_ID`、`ENABLE_SCHEDULED_SYNC`を設定する。
4. ローカルにignore済みの`.clasp.staging.json`と`.clasp.production.json`を用意する。
5. `npm install`と`npm run verify`を実行する。
6. 明示承認された環境へ`clasp`で同期する。コードをApps Script editorへ貼り付けない。
7. `当日情報媒体AI > 出力スキーマを更新`を実行する。productionでは確認文字列`PRODUCTION`を入力する。
8. `事前チェック`、dry run、通常同期、参参一覧・屋台情報まとめ・局別タブ差分同期の順に確認する。

## 日常運用

1. `当日情報媒体AI > 事前チェック`で環境、タブ、ヘッダーを検証する。
2. `ドライラン: フォーム回答を同期`で件数と要確認を確認する。dry runは入力・マスター・出力を変えず、ログだけを追記する。
3. `フォーム回答を同期`を実行し、`26処理ログ`の同じ実行IDを確認する。
4. `参参一覧を更新`でフォーム回答を1回答1行のまま同期し、参参名・企画名を確定版へ反映する。正規化後のメールアドレス、参参名、参加企画がすべて同じ回答だけを重複候補とし、該当する全行を`提出状況=確認中`、`照合結果=同一メアド・参参名・参加企画重複`にして黄色で警告する。参加企画が違う回答は別企画として警告しない。同じ参加企画内では企画名や回答日時が違っても自動的に最新1件へ絞らない。反映後は行全体を参加企画、企画名、参参名の順に自動整列するため、手動の提出状況は対象企画と一緒に移動する。
5. `局別タブを差分同期`で運スタ通常回答へ一意・完全一致した変更申請を適用し、通常企画とその他掲載情報の新規・変更・所属局移動の行だけを反映する。`企画情報`と`その他掲載情報`の色付き見出しで各区分を分け、不足セルへの手動補完を保持する。初回はデータ差分がなくても不足する見出しを追加し、回答がない区分も見出しを表示する。手動6列、回答原本、マスターは書き換えない。
6. Spreadsheetを開いたときに未対応toastが出た場合、`当日情報媒体AI > 要手動確認を開く`から`26要手動確認`を確認する。人力対応が完了した行だけ`対応状況=対応済み`とする。
7. 参参一覧で同一メアド・参参名・参加企画の黄色い行が出た場合は、原本を確認して誤回答の行だけを選択し、`当日情報媒体AI > 参参: 選択行を誤回答として除外`を実行する。警告中でない行は除外対象にならず、同じ重複グループの全行を選んだ場合も停止する。確認ダイアログ後、その回答だけが一覧から消え、残った1件の警告は自動解除される。通常の行削除では次回同期時に復活するため使わない。フォーム回答原本には書き込まない。
8. 参参変更申請と、要手動確認になった運スタ変更申請を権限者が確認する。自動で曖昧一致や部分反映をしない。
9. マスターの要確認行を権限者が解決する。自動統合はしない。
10. `参参一覧を更新`、`屋台情報まとめを更新`、`局別タブを差分同期`、または`全処理を実行`を使う。

行エラーは正常行を止めない。タブ欠落、環境不一致、必須ヘッダー欠落、マスターキー重複は全体を止める。エラー調査では行番号と列名を使い、処理ログへ原文を転記しない。

画像の一括保存は局別同期とは独立した手動操作とし、[画像処理の管理](image-processing.md)に従う。

### その他掲載情報の重複回答から正しい1件を採用する

`26要手動確認`に同じ掲載区分と企画名の重複が表示された場合、原本を確認し、**採用する正しい回答の行**を1行だけ選択して`当日情報媒体AI > その他掲載情報: 選択した回答を採用`を実行する。確認画面の企画名・所属局・部署名・原本の入力行を確認して承認する。選択した回答以外の同名のその他掲載情報は非表示の`26局別回答除外管理`へ登録し、以降の局別同期から除外する。フォーム回答原本には書き込まない。

採用操作は対象企画だけを局別タブへ反映する。旧所属局の行が1件なら手動6列とその他掲載情報の補完済みセルを保持して新所属局へ移動する。既存行がなければ追加し、複数あれば除外登録前に停止する。掲載文字情報は既存の手動入力を優先するため、再提出した掲載文字情報で既存値を上書きする機能ではない。反映後に出力を再読込して完了を確認し、当該重複グループの要手動確認行をすべて`対応済み`にする。通常の`対応状況`の手編集には回答を採用・除外する効果はない。

途中で失敗した場合は除外登録が残ることがあるが、反映を確認できない行を対応済みにはしない。出力を確認し、同じ採用操作を再実行する。通常の局別同期も除外登録を読むため旧回答は復活しない。採用後に新たな同名回答が届いた場合は再び重複確認となる。採用対象はその他掲載情報に限定し、通常企画・変更申請・参参回答には使用しない。

## 自動実行

初期状態でinstallable triggerはない。`当日情報媒体AI > 自動同期を有効化`で作成する。フォーム送信時triggerは通常提出2タブをマスターへ同期し、参参通常回答では続けて参参一覧、運スタ通常回答では続けて局別タブを差分同期する。その他掲載情報フォームはマスターを経由せず局別タブだけを差分同期する。運スタ変更申請では局別タブの差分同期と要手動確認更新だけを行い、マスター同期は起動しない。参参変更申請もマスター同期を起動しない。時間主導同期は`ENABLE_SCHEDULED_SYNC=true`の場合だけ1時間ごとに作り、マスター同期後に参参一覧、局別タブ、要手動確認も差分同期する。重複triggerは作らない。

triggerはインストールした作成者アカウントの権限で実行される。退任・異動前に後任が権限とtriggerを引き継ぐ。productionでのinstall/uninstallは確認ダイアログを必須とする。

## 緊急時のread-only確認

Apps Script editorではコードを変更しない。Execution log、projectのtrigger一覧、Script Propertiesのキーの有無、Spreadsheetのタブ名・1行目ヘッダーだけを確認してよい。実IDや個人情報をissue、チャット、commitへ貼らない。
