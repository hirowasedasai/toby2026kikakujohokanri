# 運用フロー

## 初回構築

1. 管理者がstaging用とproduction用に別々のGoogle Spreadsheetを用意し、それぞれにcontainer-bound Apps Script projectを作る。
2. 各Spreadsheetに入力5タブを正しいフォーム連携で用意する。スクリプトからは作成しない。
3. 各projectのScript Propertiesへ`APP_ENV`、`EXPECTED_SPREADSHEET_ID`、`RELEASE_ID`、`ENABLE_SCHEDULED_SYNC`を設定する。
4. ローカルにignore済みの`.clasp.staging.json`と`.clasp.production.json`を用意する。
5. `npm install`と`npm run verify`を実行する。
6. 明示承認された環境へ`clasp`で同期する。コードをApps Script editorへ貼り付けない。
7. `当日情報媒体AI > 出力スキーマを更新`を実行する。productionでは確認文字列`PRODUCTION`を入力する。
8. `事前チェック`、dry run、通常同期、参参一覧・屋台情報まとめ・局別タブ差分同期の順に確認する。

## 日常運用

1. `当日情報媒体AI > 事前チェック`で環境、タブ、ヘッダーを検証する。
2. `ドライラン: フォーム回答を同期`で件数と要確認を確認する。dry runは入力・マスター・出力を変えず、ログだけを追記する。
3. `フォーム回答を同期`を実行し、`26処理ログ`の同じ実行IDを確認する。
4. `参参一覧を更新`でフォーム回答を1回答1行のまま同期し、参参名・企画名を確定版へ反映する。正規化後のメールアドレス、参参名、参加企画がすべて同じ回答だけを重複候補とし、該当する全行を`提出状況=確認中`、`照合結果=同一メアド・参参名・参加企画重複`にして黄色で警告する。参加企画が違う回答は別企画として警告しない。同じ参加企画内では企画名や回答日時が違っても自動的に最新1件へ絞らない。反映後は行全体を参加企画、企画名、参参名の順に自動整列するため、手動の提出状況は対象企画と一緒に移動する。
5. `局別タブを差分同期`で運スタ通常回答へ一意・完全一致した変更申請を適用し、通常企画とその他掲載情報の新規・変更・所属局移動の行だけを反映する。`企画情報`と`その他掲載情報`の色付き見出しで各区分を分け、不足セルへの手動補完を保持する。初回はデータ差分がなくても不足する見出しを追加し、回答がない区分も見出しを表示する。手動6列、回答原本、マスターは書き換えない。
6. Spreadsheetを開いたときに未対応toastが出た場合、`当日情報媒体AI > 要手動確認を開く`から`26要手動確認`を確認する。人力対応が完了した行だけ`対応状況=対応済み`とする。
7. 参参一覧で同一メアド・参参名・参加企画の黄色い行が出た場合は、原本を確認して誤回答の行だけを選択し、`当日情報媒体AI > 参参: 選択行を誤回答として除外`を実行する。警告中でない行は除外対象にならず、同じ重複グループの全行を選んだ場合も停止する。確認ダイアログ後、その回答だけが一覧から消え、残った1件の警告は自動解除される。通常の行削除では次回同期時に復活するため使わない。フォーム回答原本には書き込まない。
8. 参参変更申請と、要手動確認になった運スタ変更申請を権限者が確認する。自動で曖昧一致や部分反映をしない。
9. マスターの要確認行を権限者が解決する。自動統合はしない。
10. `参参一覧を更新`、`屋台情報まとめを更新`、`局別タブを差分同期`、または`全処理を実行`を使う。

行エラーは正常行を止めない。タブ欠落、環境不一致、必須ヘッダー欠落、マスターキー重複は全体を止める。エラー調査では行番号と列名を使い、処理ログへ原文を転記しない。

チェック欄の初期値だけの空行が`入力回答と照合できない既存行`として残っている場合は、修正版のdeploy後に`局別タブを差分同期`を実行する。空行は消さず警告対象から外し、過去の空行警告は現在の局全体を再確認して、安全条件を満たすものだけ理由付きで`対応済み`にする。この限定的な自動解消以外は、上記6の人力確認を続ける。企画名のない行に手動内容が残っている場合、同じ局の古い空行警告も自動解消せず、人が確認する。要手動確認の古い行番号が現在の別企画を指していても、その企画を削除しない。

局別タブでラベルの青色が回答行へ広がった場合は、修正版のdeploy後に`局別タブを差分同期`を実行する。回答の変更がなくても9局の書式を修復する。ラベル専用色`#5b73b7`は通常セルの手動色に使用しない。その他の手動色は保持する。

局タブの`掲載媒体`・`当媒チェック`・`校閲チェック`（標準のG・H・I列）でプルダウンが消えた場合も、修正版のdeploy後に`局別タブを差分同期`を実行する。回答の差分がなくても9局を点検し、両ラベルを除いた2行目以降の既存行・未使用行について、欠落・非表示・選択肢不一致などの入力規則だけを修復する。正しい規則、選択済みの媒体・確認状態、手動入力、他列の入力規則は保持する。行追加・並べ替え後にも点検するため、ラベル隣への追加で入力規則が失われても同じ同期で復元する。掲載媒体も初期設定と自動補修で共通の定義を参照し、チェック2列だけを補修する旧版の対象漏れを防ぐ。手動で規則を消した場合は次回同期時に復旧する。

日時4列の注意書き付きヘッダーへの対応版をdeployした後は、`局別タブを差分同期`で既存回答の`企画日時`も補完できる。フォームの再提出は不要。反映例は`11/7 10:00〜17:00 / 11/8 10:00〜17:00`。手動6列は変更しない。

画像の一括保存は局別同期とは独立した手動操作とし、[画像処理の管理](image-processing.md)に従う。

### その他掲載情報の重複回答から正しい1件を採用する

`26要手動確認`に同じ掲載区分と企画名の重複が表示された場合、原本を確認し、**採用する正しい回答の行**を1行だけ選択して`当日情報媒体AI > その他掲載情報: 選択した回答を採用`を実行する。確認画面の企画名・所属局・部署名・原本の入力行を確認して承認する。選択した回答以外の同名のその他掲載情報は非表示の`26局別回答除外管理`へ登録し、以降の局別同期から除外する。フォーム回答原本には書き込まない。

採用操作は対象企画だけを局別タブへ反映する。旧所属局の行が1件なら手動6列とその他掲載情報の補完済みセルを保持して新所属局へ移動する。既存行がなければ追加し、複数あれば除外登録前に停止する。掲載文字情報は既存の手動入力を優先するため、再提出した掲載文字情報で既存値を上書きする機能ではない。反映後に出力を再読込して完了を確認し、当該重複グループの要手動確認行をすべて`対応済み`にする。通常の`対応状況`の手編集には回答を採用・除外する効果はない。

途中で失敗した場合は除外登録が残ることがあるが、反映を確認できない行を対応済みにはしない。出力を確認し、同じ採用操作を再実行する。通常の局別同期も除外登録を読むため旧回答は復活しない。採用後に新たな同名回答が届いた場合は再び重複確認となる。採用対象はその他掲載情報に限定し、通常企画・変更申請・参参回答には使用しない。

### 同じ企画・掲載媒体・文字情報参照先は後の申請を採用する

その他掲載情報は、同じ企画であると確認でき、掲載媒体と掲載文字情報の参照先も両方同じ場合に限り、原本の`タイムスタンプ`が最も新しい回答を正として局別出力を整理する。企画名が明確に異なるものは、媒体・参照先が同じでも別企画として保持する。名前が似ている、または表記ゆれに見えるだけでは統合せず、同一企画か確認する。別企画と確認済みの回答、媒体または参照先が異なる回答も残す。参照先の比較ではURLの一部を省略せず、文書内のタブ・見出し等の指定も保持する。

原本フォームには掲載媒体の列がないため、局別出力の`掲載媒体`と原本の企画名・参照先・申請日時を照合して判断する。媒体が空欄、原本と出力の対応が曖昧、申請日時が同じまたは不明の場合は推測して統合しない。この判定は権限者による整理手順であり、現在の自動同期が媒体・参照先だけで最新回答を選ぶ機能ではない。

整理前にバックアップを取得する。採用行の手動入力を保持し、旧行にだけ手動情報がある場合は内容を確認してから引き継ぐ。旧回答の識別子・除外日時・後続回答を採用した理由を`26局別回答除外管理`に記録してから、局別出力の旧行を削除する。同名回答用の採用メニューを、異なる媒体・参照先の回答を含むグループへ一括適用しない。原本1件から重複している出力だけを整理する場合は、その原本自体を除外しない。

原本の不変、採用行の保持、旧回答の再生成がないこと、対象の重複警告が解消したことを確認してから`26要手動確認`を`対応済み`にする。除外管理タブは作業後に非表示へ戻す。今後の新たな回答も同じ基準で確認する。

### 同名の通常回答をそれぞれ別企画として残す

担当者が別企画であると確認した場合、`26要手動確認`で同名グループの通常回答をすべて選択し、`当日情報媒体AI > 通常企画: 選択した同名回答を別企画として登録`を実行する。企画名・所属局・原本行を確認して承認する。複数の同名グループを一度に選択できるが、一部の回答だけの選択やその他掲載情報は対象外。

確認結果は非表示の`26局別確認結果`へ保存する。初回は既存行の所属局・部署名・担当者名・企画紹介文・ゲスト情報の完全一致で回答を結び付け、一意でなければ登録前に停止する。既存の手動6列を保持して不足回答を追加し、対象局の末尾に非表示の`同期回答識別子`を追加する。以後は回答識別子で行を区別し、公開企画名は変えない。出力を再読込して反映を検証してから該当確認行を対応済みにする。

新しい同名回答や原本内容の変化があれば以前の承認を引き継がず再確認する。同名別企画への変更申請は企画名だけでは対象を特定できないため、引き続き手動確認する。この機能は局別同期のための確認結果であり、マスターの衝突判定・その他掲載情報の媒体別判定は変更しない。

### 文字情報の異なるその他掲載情報を別々に残す

掲載文字情報が異なり両方必要な回答は、同じ企画名・同じ媒体でも別の掲載情報として扱う。`26要手動確認`または`26運スタ企画その他掲載情報`で、同じ企画名の回答をすべて選び、`当日情報媒体AI > その他掲載情報: 文字情報の違う回答を別々に登録`を実行する。原本タブでは選択だけを行い、値を編集しない。原本1件に対する既存行の照合にも利用できる。

初回は掲載文字情報・所属局・部署名・担当者名を完全一致で照合する。本文の比較は改行コードと前後空白だけを正規化する。原本で掲載文字情報が空欄・同一の回答がある場合や、編集済み本文などにより既存行と一意に照合できない場合は登録前に停止する。媒体は識別条件に使わない。文字情報がリンクの場合はリンク値を照合し、リンク先本文を自動判定しない。原本や既存行を自動削除・統合せず、台帳へ`別掲載情報`を記録する。

以後は`同期回答識別子`で対応付け、校閲した掲載文字情報・媒体・チェック・その他の手動補完を保持する。原本の変化や新たな同名回答では再確認する。異なる本文の全回答を残すこの操作と、誤回答を除外して正しい1件を採用する操作は目的が異なる。

### 書式不備の変更申請を原本を残して補正する

変更内容を原本で確認した権限者が、`26要手動確認`の該当変更申請を1行選び、`当日情報媒体AI > 変更申請: 選択行の書式を補正して反映`を実行する。補正した変更前・変更後をそれぞれ`項目名：「内容」`の形式で入力し、確認画面で内容を確認する。元のフォーム回答と変更申請は編集しない。

補正は既存の安全条件（企画の一意性、局・部署一致、変更前の完全一致、変更項目集合一致、画像変更なし、手動列上書き禁止）を通過した場合だけ反映する。対象行の`変更反映状況`は`確認済み補正を反映`とする。補正内容と原本の照合値を`26局別確認結果`に保存するため、通常同期でも補正が再適用される。原本変更時は適用を停止する。

登録後の出力エラーでは台帳が残る場合がある。`局別タブを差分同期`で再試行し、実際の反映と完了更新を確認する。未反映の行を先に対応済みにしない。処理ログには入力行とエラーコードだけを残し、補正本文や担当者名を残さない。

申請名と掲載名が違う場合は、原本の担当者・部署・紹介文・ゲストなどから対象を照合し、`変更申請: 変更先を指定して補正・反映`を使う。通常回答の識別子（入力タブ名と行番号）を指定し、補正前後と確認画面の変更先を確認する。申請と対象の双方を照合値で固定するので、原本変更後は再確認となる。局・部署や現在値の検証は省略しない。申請に開催日がないなど内容自体が不明な場合は、確認が取れるまで登録しない。

### 同一企画の通常再提出を採用する

同一企画の更新として提出されたと確認できた場合だけ、`26要手動確認`で最新の通常回答を1行選択し、`通常企画: 確認した再提出の最新回答を採用`を実行する。同名・同局・同部署・同担当者で、一意に最新の受付日時がある回答だけを採用できる。名称の違う企画は保持し、同名でも内容の異なる別企画なら前述の別企画登録を使う。

確認画面にはまとめる回答識別子を表示する。台帳に同名回答全件の照合値を保存し、局別の手動列を保持したまま採用回答の自動列だけを反映する。原本は変更せず、旧回答も残す。出力検証後にグループの確認行を完了にする。新しい回答・原本変更・別企画承認との競合があれば更新を止め、再確認する。その他掲載情報・マスター・参参一覧の採用条件は変更しない。

## 自動実行

初期状態でinstallable triggerはない。`当日情報媒体AI > 自動同期を有効化`で作成する。フォーム送信時triggerは通常提出2タブをマスターへ同期し、参参通常回答では続けて参参一覧、運スタ通常回答では続けて局別タブを差分同期する。その他掲載情報フォームはマスターを経由せず局別タブだけを差分同期する。運スタ変更申請では局別タブの差分同期と要手動確認更新だけを行い、マスター同期は起動しない。参参変更申請もマスター同期を起動しない。時間主導同期は`ENABLE_SCHEDULED_SYNC=true`の場合だけ1時間ごとに作り、マスター同期後に参参一覧、局別タブ、要手動確認も差分同期する。重複triggerは作らない。

triggerはインストールした作成者アカウントの権限で実行される。退任・異動前に後任が権限とtriggerを引き継ぐ。productionでのinstall/uninstallは確認ダイアログを必須とする。

## 緊急時のread-only確認

Apps Script editorではコードを変更しない。Execution log、projectのtrigger一覧、Script Propertiesのキーの有無、Spreadsheetのタブ名・1行目ヘッダーだけを確認してよい。実IDや個人情報をissue、チャット、commitへ貼らない。
