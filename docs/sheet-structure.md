# シート構成

## 入力（書き込み禁止）

| シート | 用途 | 優先度 |
| --- | --- | ---: |
| `26参参フォーム回答` | 通常フォーム回答の生データ | 10 |
| `26運スタ企画フォーム回答` | 運営スタッフ企画フォーム回答の生データ | 10 |
| `26参参変更申請` | 参加団体・参加者企画の変更申請原本 | 自動同期対象外 |
| `26運スタ企画変更申請` | 運営スタッフ企画の変更申請原本 | 自動同期対象外 |

スクリプトは入力タブの作成、ヘッダー補正、値更新、書式変更、削除を一切行わない。4タブのどれか、またはヘッダー行が欠ける場合は同期開始前に停止する。通常提出2タブは`config.gs`の候補ヘッダーで列を解決し、必須列も検証する。`26運スタ企画フォーム回答`の参加企画だけは、フォームに同名質問がないため固定値`運営スタッフ企画`を読み取り時に補う。

変更申請2タブはマスターへ自動反映しない。運スタ変更申請だけは、フォーム送信時トリガーで局別タブを差分同期し、後述の厳格な条件を満たした変更を局別表示へ反映する。参参変更申請は引き続き権限者が原本を確認してマスターへ明示反映する。

## `26掲載情報マスター`（正本）

| 必須列 | 意味 |
| --- | --- |
| `管理ID` | 正式ID、または`TMP-`で始まる暫定ID。既存更新時は維持 |
| `メールアドレス` | 連絡先。出力と処理ログには含めない |
| `参加企画` | 参加区分。飲食物抽出にも利用 |
| `所属局` | 運営スタッフ企画の所属局。参加団体企画と追加前の回答では空欄可 |
| `団体名` | 掲載団体名 |
| `企画名` | 掲載企画名 |
| `販売物` | 掲載する販売品目 |
| `画像リンク` | 掲載画像へのリンク |
| `データソース` | 採用した入力タブ名 |
| `同期ステータス` | `同期済み`または`要確認` |
| `最終更新日時` | 内容が実際に変わった日時 |
| `要確認` | `TRUE`/`FALSE` |
| `要確認理由` | PIIを含まない制御された理由 |

列順は固定しない。1行目のヘッダー名で位置を解決する。追加列は同期時にそのまま保持する。

## 出力

`参参一覧`の列は`管理ID`、`参加企画`、`所属局`、`団体名`、`企画名`、`販売物`、`画像リンク`、`最終更新日時`。`屋台情報まとめ`は`管理ID`、`参加企画`、`所属局`、`団体名`、`企画名`、`販売物`、`画像リンク`、`要確認`。

どちらもマスターの`同期済み`かつ要確認でない行だけを使う。出力タブのヘッダーはsetupで作成し、通常の出力更新はヘッダーを上書きしない。いずれかの生成結果が0件となり既存データがある場合は、安全弁で既存データを維持する。正当に0件へ変更する場合も、原因確認後に権限者が明示対応する。

## 局別作業タブ

フォームの`所属局`選択肢に対応する作業場所として、`26会場整備局`、`26参加対応局`、`26開発局`、`26企画局`、`26広報制作局`、`26渉外局`、`26総務局`、`26財務局`、`26超局PJ`を用意する。前年資料の`はじめに`タブは作成しない。

9タブは`26運スタ企画フォーム回答`を`所属局`で振り分ける差分同期型の作業タブである。自動管理列は`企画名`、`企画紹介文`、`担当者名`、`部署名`、`企画場所`、`企画日時`、`企画ジャンル`、`整理券情報`、`ゲスト情報`、`備考`、`変更反映状況`、`最終変更申請日時`とする。手動管理列は`内部向け企画・取り組み名`、`掲載文字情報`、`ページ名`、`掲載媒体`、`当媒チェック`、`校閲チェック`の6列とし、合計18列とする。所属局はタブ名で分かるため列に重複表示せず、メールアドレスも出力しない。

列順は前年の局別作業タブに合わせ、`ページ名`、`内部向け企画・取り組み名`、`企画名`（前年の外部向け企画・取り組み名）、`掲載文字情報`、`担当者名`、`部署名`、`掲載媒体`、`当媒チェック`、`校閲チェック`、`変更反映状況`、`企画日時`、`企画場所`の順とする。前年にない`企画紹介文`、`企画ジャンル`、`整理券情報`、`ゲスト情報`、`備考`、`最終変更申請日時`は右端へ置く。`フォーム提出`はフォーム回答から生成された行であること自体が提出済みを示すため、重複列として追加しない。

局別差分同期は企画名をNFKC正規化、前後空白除去、連続空白統一、小文字化して一意照合する。運スタ変更申請の`変更前`と`変更後`を行単位の`項目名：「内容」`として解析し、企画名が1件だけ一致し、所属局・部署名・項目集合・現在値が一致した場合だけ、メモリ上の企画情報へ原子的に適用する。その後、新規行の追加、内容が変わった行の自動管理列更新、所属局が変わった行の移動だけを書き込む。全データ行の消去・再生成は行わない。

手動6列は既存値をそのまま保持し、コードから上書きしない。新規行だけ`内部向け企画・取り組み名=企画名`、`掲載文字情報=企画紹介文`、両チェック=`未確認`で初期化する。原典の`企画紹介文`が変わった場合と、利用者が`掲載文字情報`を編集した場合は、当媒・校閲チェックだけを`未確認`へ戻す。`掲載文字情報`は変更申請から自動更新しない。

同じ18ヘッダーが別順序で既に存在する場合、次回のスキーマ確認または局別差分同期時にヘッダー名で値を対応づけて上記順序へ移行する。列番号は固定せず、手動6列の既存値も保持する。

入力と照合できない既存行は削除せず保持し、重複、画像変更、企画名・所属局・部署名の不一致、記法不正、未対応項目、変更前不一致とともに`26要手動確認`へ送る。所属局移動は移動先へ手動列を含む行を書いた後に移動元の該当行だけを削除する。入力4タブの回答原本は移動・書き換えない。数式として評価され得る`=`始まりの自動出力値は文字列として書き出す。

## `26要手動確認`

自動反映できなかった運スタ変更申請、重複した通常回答、入力と照合できない既存局別行を、`確認キー`、受付日時、所属局、部署名、企画名、担当者名、要確認理由、変更前後、変更前後画像、入力タブ、入力行、`対応状況`で保持する。確認キーは入力タブ名と行番号から作り、確認キー単位で追加・差分更新する。既存の`対応状況`と過去行は自動削除・上書きしない。初期値は`未対応`、運用者が完了を確認したら`対応済み`へ変更する。

未対応が1件以上あればタブ色を赤にし、Spreadsheetを開いたときに未対応件数をtoast通知する。自動トリガー実行中は利用者画面へmodalを出せないため、このタブを永続的な対応待ちキューとする。

## `26処理ログ`

列は`実行ID`、`記録日時`、`環境`、`処理`、`レベル`、`エラーコード`、`入力タブ`、`行番号`、`列名`、`説明`、`新規件数`、`更新件数`、`スキップ件数`、`要確認件数`、`リリースID`。

メール、入力行全体、自由記述本文、画像URLは記録しない。ログ閲覧権限は運用担当者に限定する。
