# アーキテクチャ

## 境界

システムはGoogle Sheetsとcontainer-bound Apps Scriptだけで構成する。外部DB、Cloud Run、FastAPI、OpenAI API、外部秘密管理、外部URLアクセス、Webアプリ公開は使わない。Apps Script本体にnpm runtime依存はなく、npmはローカル検証と`clasp`操作だけに使う。

stagingとproductionは、スプレッドシートもApps Script projectも完全に別である。各scriptはScript Propertiesの`EXPECTED_SPREADSHEET_ID`と実際のバウンド先IDを毎回照合する。`APP_ENV`が`staging`または`production`以外でも停止する。

## データフロー

```text
入力4タブ（read-only）
        │ ヘッダー解決・行検証・キー判定
        ▼
26掲載情報マスター（掲載情報の唯一の正本）
        │ メモリ上で出力全体を構築・検証
        └──────────► 屋台情報まとめ

26参参フォーム回答（read-only）
        │ メール＋参加企画で提出管理へ差分同期
        └──────────► 参参一覧（フォーム回答を確定版へ反映）

運スタ通常回答・変更申請（read-only）
        │ 企画名照合・変更記法解析・行単位差分
        ├──────────► 局別9タブ（自動12列＋手動6列）
        └─曖昧・不一致─► 26要手動確認

各処理 ──サニタイズ済み要約──► 26処理ログ
```

同期は`LockService.getScriptLock()`で直列化する。全タブと必須ヘッダー、環境一致を開始前に確認し、致命的な不整合時にはマスターと出力を変更しない。入力は常に`getValues()`で一括取得する。屋台情報まとめはメモリ上で完成させてから一括反映する。参参一覧はフォーム回答の参参名・企画名を確定版へ差分反映し、既存行を削除しない。差分反映後は行全体を参加企画、企画名、参参名の順に並べ替え、手動の提出状況を同じ行に保持する。局別9タブも既存行と希望状態を企画名で比較し、新規・内容変更・所属局移動の行だけを書き込む。照合できない既存行は自動削除しない。

Apps Script/Sheetsには複数シートをまとめたACID transactionがない。このため`runAll`は同一lock内で同期、参参一覧、屋台情報まとめ、局別9タブ、要手動確認の順に処理し、各段階をログに残す。変更申請は全項目を検証してからメモリ上の企画情報へ原子的に適用し、一部変更だけを書かない。所属局移動は移動先へ手動6列を含む行を書いた後、移動元の該当行だけを削除する。途中失敗で重複が残っても次回同期は自動統合せず、要手動確認へ送る。

局別タブの手動6列はコードの上書き対象外である。初回追加時だけ初期値を設定し、通常の差分同期と復旧用の全件照合のどちらでも既存値を保持する。原典の企画紹介文または掲載文字情報が変わったときだけ、当媒・校閲チェックを`未確認`へ戻す。

参参一覧の照合キーは正式企画IDではなく、正規化した`メールアドレス + 参加企画 + 企画名`とする。フォーム回答が一意なら参参名と企画名を回答列・確定版へ反映し、同じ提出者の別企画は別行にする。3項目が同じ一覧内または回答内の重複は`照合結果`とサニタイズ済みログへ送り、曖昧な回答を自動採用しない。ただし、画像リンク以外の同期項目と入力タブが一致し、全回答日時から最新を一意に決められる再送は、その最新回答を採用してINFOログを残す。旧ルールの企画名空欄の重複行は1企画目へ再利用する。フォーム回答がない既存行と、人が設定した`確認中`・`キャンセル`は保持する。

## キーと競合

正式企画IDがある行は正規化済み正式IDをキーにする。ない行だけ、NFKC Unicode正規化・trim・メール小文字化後の`メールアドレス + 参加企画 + 企画名`を暫定キーにする。暫定管理IDは予約prefix`TMP-`と決定的hashから生成するため、再実行しても同じIDになる。同じメールアドレスでも企画名が異なれば別企画として同期する。

既存行を更新しても`管理ID`は変更しない。暫定キー衝突やキー変更疑いは原則として自動統合せず、`要確認`と理由を付けてログに残す。画像リンクだけを更新した時系列の明確な再送は最新回答を採用し、旧衝突の`要確認`を解除する。既存マスター自体にキーまたは管理IDの重複があれば開始前エラーとして停止する。

## セキュリティと監査

manifest scopeは現在のスプレッドシート操作とtrigger管理だけに限定する。ログは入力行全体、メールアドレス、自由記述本文を保存せず、実行ID、環境、処理名、行番号、列名、エラーコード、制御された短い説明、件数、リリースIDだけを記録する。説明に混入したメールとURLは置換する。

productionではテストデータ投入、全消去、危険な初期化を行う関数を提供しない。スキーマ作成は通常同期から分離した`setupProductionSchema`だけで、環境照合と`PRODUCTION`入力確認を必須とする。
